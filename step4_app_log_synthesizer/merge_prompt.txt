===============================================================================
PROCESS
===============================================================================


1. Group verified fragments by date. This produces the initial meaningful
   session + calendar event skeleton.
2. Merge only verified meaningful fragments that share a date + contact into
messenger.meaningful_sessions where natural (don't force merges across unrelated fragments).

 IMPORTANT: In this step, "merge" means preserve, not summarize.

Merging is optional. Preservation is mandatory. An isolated verified fragment
must never be dropped just because there is nothing to merge with.

For every verified messenger fragment:
- all original messages from that fragment must appear in the final app log;
- message text must be copied verbatim or near-verbatim;
- do not keep only the first and last message;
- do not drop middle messages;
- do not replace the fragment with a shorter paraphrase;
- do not move verified messages to messenger.filler_sessions.

If multiple same-date + same-contact fragments make one session too long,
split them into multiple messenger.meaningful_sessions with the same date
and contact. Preservation is mandatory; compactness is optional.

If a verified messenger fragment has no compatible same-date + same-contact
fragment to merge with, keep it as its own messenger.meaningful_sessions item.

If a verified calendar fragment has no compatible same-date event to merge
with, keep it as its own calendar.events item.


3. Compute meaningful_token_count and target_total_filler_tokens.
4. Select a subset of VERIFIED DECOYS that fits the decoy budget.   Do not create new decoys.
5. Place selected decoys


For messenger decoys:


- First apply contact_policy:
  - if contact_policy = specific, preferred_contact is the only allowed contact;
  - if contact_policy = flexible, the final contact may be chosen during placement.


- Then decide placement using placement_hint:
  - if placement_hint = same_contact_meaningful_session, prefer insertion into a compatible meaningful session that satisfies contact_policy;
  - if placement_hint = separate_filler_session, prefer a separate messenger.filler_sessions entry that satisfies contact_policy;
  - if placement_hint = flexible, choose the more natural and safer placement that satisfies contact_policy.


- If the decoy is inserted into an existing meaningful messenger session:
  - use that session’s contact as the final contact;
  - replace sender = "contact" with that session’s contact name.


- If the decoy is placed as a separate messenger.filler_sessions entry:
  - if contact_policy = flexible, choose an existing contact from CORRECTED SOCIAL CIRCLE;
  - if contact_policy = specific, use preferred_contact.




For calendar decoys:
- convert the decoy into one calendar.events entry;
- assign final event_id, date, start_time, and end_time;
- do not overlap the decoy with meaningful calendar evidence.


Distribute placed decoys evenly and naturally as much as possible across the log window, while preserving realistic contact, date, and app-surface balance.


6. Generate mundane filler to fill the remaining filler budget.
7. Distribute mundane filler and selected decoys across days and contacts to
   meet temporal and contact balance rules.
8. Build the cross_app_index and token_stats.


9. Build decoy_registry for selected decoys.
For every placed decoy:
- related_item_id must point to the final session_id or event_id where the
decoy appears;
- placement_type must be one of:
meaningful_session_insert | filler_session | calendar_event;
- message_indices must identify decoy messages if the decoy is placed in a
messenger session;
- message_indices must be null for calendar decoys.


10. Run SIMPLE DECOY CHECK.
    If any selected decoy fails, remove it and replace it with mundane filler.

11. Run VERIFIED FRAGMENT COMPLETENESS CHECK.

Build a global key for every input verified fragment:

global_fragment_key =
  source_cluster_id + "::" +
  fragment_id + "::" +
  date + "::" +
  fragment_type + "::" +
  source.type + "::" +
  source.name

Do not use fragment_id alone as a unique key.

For every input verified fragment, add exactly one entry to
verified_fragment_registry.

Each registry entry must include:
- source_cluster_id
- source_fragment_id
- global_fragment_key
- placed_item_id
- hidden_fact_ids
- status: "placed" | "missing" | "duplicate"
- content_anchors

Placement rules:
- A messenger fragment is "placed" only if every original message appears verbatim or near-verbatim in the final M-xxx session referenced by placed_item_id.
- For messenger fragments, content_anchors must include one exact 5-12 word phrase from each original message, and all anchors must appear in that same M-xxx session.
- A calendar fragment is "placed" only if its original title, location, participants, and notes appear verbatim or near-verbatim in the final E-xxx event referenced by placed_item_id.
- For calendar fragments, content_anchors must include exact phrases from the original title, notes, and location if present, and all anchors must appear in that same E-xxx event.


The completeness_check passes only if:
- verified_fragment_registry contains exactly one entry for every input verified fragment;
- every registry entry has status = "placed";
- every placed_item_id points to a final M-xxx meaningful session or E-xxx calendar event;
- every required content_anchor appears in the final raw app-log item named by placed_item_id;
- no filler session or decoy-only item is counted as verified-fragment evidence;
- every hidden_fact_id supported by placed verified fragments appears in at least one cross_app_index.hidden_fact_ids_touched entry.

If any check fails:
- repair the merge before output;

12. Emit the output JSON.
