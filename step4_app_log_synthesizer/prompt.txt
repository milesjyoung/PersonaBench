SYSTEM:


You receive ONE hidden-fact cluster that was already formed by a prior clustering stage. Do not recluster, drop, split, merge, or add hidden facts.
A cluster should usually contain 2-3 naturally related hidden facts.

For this cluster, you generate 4~5 shared app-log fragments which should be implicit about a persona.
This fragment generation stage is a part of a reverse-inferability pipeline.

Each fragment is one app-log artifact:
- one messenger session containing 3-4 messages, or
- one calendar event.

Each fragment encodes the hidden facts through behaviors alone, never through explicit labels or
categorical words.

No single fragment should fully reveal an ordinary hidden fact downstream.
A downstream reviewer could read and
infer a hidden fact only by combining multiple shared fragments.


You do NOT see the full persona profile, unrelated hidden facts outside this cluster, the full app log, or the filler content.
You see only this hidden-fact cluster and the persona's corrected social circle.
This scoping is deliberate — it prevents cross-contamination between facts
while allowing naturally related facts within the cluster to share evidence.


This prompt is self-contained. All required data is inserted below.

BEHAVIORS, NEVER LABELS
===============================================================================

The single most important rule. Under NO circumstance may a fragment contain:

- The clinical / categorical label in any `hidden_fact.ground_truth_label`
  in this cluster or a close synonym.
- Any word that directly names the condition, identity, or category that the
  fact describes (e.g., if the fact is "Generalized Anxiety Disorder +
  sertraline", fragments may not contain "anxiety", "GAD", "SSRI",
  "antidepressant", "depression", "mental health", "therapist", "panic
  attack", or any clinical synonym). Do not use category-adjacent phrases that strongly imply the label,
  even if they are not exact synonyms.
- Diagnostic or explanatory language from a first-person narrator explaining
  any hidden fact in this cluster. ("I take my SSRI because of anxiety" is forbidden).

Instead, express the fact through BEHAVIORS and CONTEXT:

- Routine artifacts: medication pick-up at 7:15 AM; biweekly Thursday 3pm
  video call; refill alert from Walgreens on the 14th.
- Logistical artifacts: pharmacy pickup notifications, copay amounts, refill
  reminders, or generic prescription references ("your refill is ready,"
  "$11 copay," "90-day supply picked up") WITHOUT naming the specific
  medication when the medication itself is part of the ground_truth_label.
  The inference must come from the behavioral pattern (pharmacy visits,
  regular pickups, copay amounts), not from reading a drug name.
- Relational artifacts: a family member's offhand supportive line; a friend
  rescheduling because "Dr. Patel's slot moved"; a calendar entry "weekly
  video w/ Dr. P" with no explanatory note.
- Environmental artifacts: cross-app signals that only cohere when combined
  — a chat says "picked up my Thursday pill" and the calendar has a
  "Walgreens" event on the same Thursday.

The test: if a reader saw just one fragment alone, they  might think one or more hidden facts
are plausible, but should not be CERTAIN about any ordinary hidden fact.

If a reader saw the full 4-5 fragment cluster, they should be able to infer
every hidden fact in the cluster with high confidence.
The cluster should work by accumulation: each fragment contributes partial
evidence, and the hidden facts become clear only when the shared fragments are
read together.

===============================================================================
SHARED FRAGMENT DESIGN RULES
===============================================================================

You receive one pre-formed hidden-fact cluster.

Do NOT recluster, split, merge, drop, or add hidden facts.

Generate 4-5 shared fragments total for this cluster.
Do NOT generate separate 2-3 fragments per hidden fact.
The generated fragments must satisfy all rules below:


1. SHARED EVIDENCE

Fragments must be truly shared. That is, every fragment must support 2 or more hidden facts through partial clues.

Each fragment should provide only a partial clue for each hidden fact it supports. That is,
Every fragment must be useful but incomplete: it should contribute evidence, not explain the hidden fact.

A reviewer should need to combine multiple fragments to infer each hidden fact.

Good pattern:
- F1 supports HF-A + HF-B
- F2 supports HF-A + HF-C
- F3 supports HF-B + HF-C
- F4 supports HF-A + HF-B
- F5 supports HF-B + HF-C

Bad pattern:
- F1, F2 support only HF-A
- F3, F4 support only HF-B
- F5 supports only HF-C

The bad pattern is separate per-fact evidence, not a shared cluster.
If that happens, such fragment should be rewritten.

2. MINIMUM SUPPORT

Each hidden fact must be supported by at least 2 fragments.
Prefer 3 or more supporting fragments for a hidden fact when this can be done
naturally within the 4-5 fragment cluster.
No single fragment should make the hidden fact fully inferable on its own.
The hidden fact should become strongly inferable only when its supporting
fragments are combined.


3. SOURCE DIVERSITY

Use at least 2 sources across the cluster.

A source is either:
- one social-circle contact, or
- the calendar.

Do not put all evidence into one messenger thread.

4. CALENDAR USE

Use at least one calendar event if any hidden fact involves time, such as:
- routine
- appointment
- deadline
- payment cycle
- trip
- caregiving schedule
- recurring obligation

5. CONCRETE DETAILS are preserved wherever the hidden facts in this cluster provide them:
   - amounts  — include the actual number.
   - Medication names, dosages (but never the reason for taking the med).
   - places, streets, neighborhoods, clinics, schools, workplaces, stores
   - Dates and times with specificity (not "next week" — "Thursday the 24th
     at 6:30 AM").
   - Named people outside the 5 social circle members (Dr. Patel, coworker
     "Jamal from data team", neighbor "Mrs. Ito", cat "Oliver").
     Concrete details should anchor the inference, not state the conclusion.
6. CONTACT BALANCING: check the `contact_usage_counts` input. Prefer contacts
   who have FEWER previous meaningful sessions for this persona, so the full
   log doesn't skew one contact to 60%+. If every contact is balanced, use
   the social circle member whose `shared_activities` or
   `recent_text_topics` best matches this cluster.
7. TIMESTAMPS: Every fact-bearing fragment must include a realistic timestamp
   within the log window. Messages within a session should have
   intervals drawn from this distribution: 60% of gaps are 1-5 minutes,
   25% are 5-15 minutes, 10% are 15-45 minutes, 5% are 1-24 hours
   (cross-day replies). Never use uniform gaps.
8. VOICE: each contact should sound like their `personality_mini_profile`
   and `communication_style` in the social circle. No homogeneous voice.
9. FRAGMENT ORDER: within the log window, fragments for the cluster should
   distribute across multiple days, not bunch on one day or at the end of
   the window. If the fact is temporal (routine, recurring), spread supporting
   fragments across at least 2 different weeks when possible.
10. NO SINGLE-FRAGMENT REVEAL: No ordinary hidden fact should be fully revealed
  by one fragment alone. The full 4-5 fragment cluster should make every hidden fact strongly inferable.

===============================================================================
WHAT FRAGMENTS MUST NOT CONTAIN
===============================================================================

- Explicit labels (see BEHAVIORS, NEVER LABELS above).
- Meta-commentary about being a persona, a test, or a benchmark.
- The fact_id, ground_truth_label, or any internal schema field in the text
  itself. Those go in the fragment's metadata, not the content.
- Session IDs, event IDs, or other pipeline artifacts in the user-visible
  text.
- Small-talk philosophy or essay-style reflection. Filler is generated
  separately; this prompt produces meaningful fact-bearing content only.
- Any two fragments that cite identical timestamps or near-identical
  wording — duplicates will fail verification.
- Over-explanation that tells the reader what to infer.

Filler content is generated separately. This prompt produces meaningful fact-bearing content only.

===============================================================================
PROCESS
===============================================================================

1. Read the hidden-fact cluster carefully. Identify:
   - concrete details in the fact (medication names, dollar
     amounts, dates, places, contacts, routines, organizations, locations, or recurring times),
   - forbidden labels or close synonyms that must not appear in user-visible text
   - behaviors, routines, logistics, or app-log artifacts that could make the
     fact inferable without naming it

2.  Do not recluster. This prompt receives one pre-formed hidden-fact cluster.
Do not split, merge, drop, add, or recluster hidden facts.

3.  Plan shared evidence for this cluster.

   - generate 4-5 fragments total
   - make every fragment support 2 or more hidden facts
   - ensure each hidden fact is supported by at least 2 fragments
   - prefer 3 or more supporting fragments per hidden fact when natural
   - ensure the hidden fact becomes strongly inferable only by combining its
     supporting fragments

4. Read the social circle. Identify:
   - Which contacts have `shared_activities` or `recent_text_topics` that
     make them natural participants in fragments for this cluster.
   - Which contacts have low previous session counts in
     `contact_usage_counts` (rebalance opportunity).
5. Plan source and time distribution.

   For this cluster, decide:
   - which fragments are messenger sessions and which are calendar events
   - which contact or calendar source each fragment uses
   - which date and time each fragment uses within the log window
   - how fragments are spread across days or weeks
   - how each fragment supports multiple hidden facts

6. Draft each fragment.

   Each fragment must be one app-log artifact:
   - one messenger session with 3-4 messages, or
   - one calendar event

   Include either `messages` OR `calendar_event` depending on `fragment_type`.
   The other field must be null.

   As you write, verify that every user-visible text field passes the
   "behaviors, never labels" test.  After drafting each fragment, ask whether a reader could infer a
   hidden fact from this fragment alone. If yes, weaken or split the clue.

7. Build the support mappings.

   produce:
   - `supports_hidden_facts` inside each fragment
   - `hidden_fact_ids` at the cluster level: the list of all hidden facts in this cluster

   Confirm that these mappings are consistent.

8. Fill `coverage_check`  and repair if needed.

For this cluster, set each `coverage_check` field based on the generated fragments.

If any required check would be false, revise the fragments before output.
Do not emit JSON with a failed required check unless the failure is impossible to repair.

required checks :
- the cluster has 2-3 hidden facts and 4-5 fragments
- each hidden fact is supported by at least 2 fragments
- 3 or more supporting fragments are used when natural
- every fragments supports 2 or more hidden facts.
- no single ordinary fragment fully reveals a hidden fact
- combined supporting fragments make each hidden fact strongly inferable
- at least 2 sources are used
- calendar is used when the cluster has a temporal dimension
- timestamps, contact choices, and message cadence are realistic

If a check cannot be repaired, set the field to false and explain why in
`coverage_check_notes`.

9. Emit the output JSON.

End of prompt.
